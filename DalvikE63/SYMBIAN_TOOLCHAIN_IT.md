Gli hash Nokia MD5/SHA1 provengono dai metadati del *mirror*, non da una firma ufficiale Nokia: confermano che il download è identico a quello archiviato, **non** autenticità/diritti di redistribuzione del mirror. Gli SHA-256 sono misurati in questa sessione e fissati nello script. Nel file ZIP Nokia è incluso `Nokia_EULA.txt`: conferisce diritti d’uso limitati a un computer, restringe modifica e ridistribuzione e il readme avvisa che l’SDK poteva richiedere registrazione. **Leggere personalmente la licenza prima di installare/patchare**; il bootstrap richiede `NOKIA_SDK_LICENSE_ACCEPTED=1`. Non pubblichiamo ZIP, header, librerie, installazione SDK o copie dell’SDK modificate. La disponibilità storica dell’SDK non equivale a permesso di ridistribuzione.

Per Debian 13, in questa sessione sono serviti `libc6-i386 lib32z1 lib32stdc++6 bison flex unshield`, oltre a `gcc g++ perl make patch zlib1g-dev libssl-dev curl unzip python3 openssl`. I sorgenti GnuPoc del 2012 necessitavano dei fix per GCC14, glibc moderna e API OpenSSL 3 in [`tools/patch_gnupoc_122.py`](tools/patch_gnupoc_122.py): lo script è stato verificato **due volte su un tarball GnuPoc pulito**, seguito da build reale degli strumenti EKA2. Il Perl moderno richiedeva due correzioni sintattiche *nella copia SDK locale* via [`tools/patch_sdk_perl.py`](tools/patch_sdk_perl.py). Le patch sono riproducibili, ma la loro compatibilità legale con la EULA va valutata da chi installa.

**Per il nuovo diagnostico AOSP 0.6:** il percorso predefinito dei tre script `tools/bootstrap_symbian_fp1.sh`, `tools/build_symbian_fp1.sh` e `tools/build_aosp42_object_diagnostic_sis.py` è adesso `DalvikE63/build/toolchains/`, cartella esclusa dallo snapshot. Le righe con `~/build/e63-local/` sotto descrivono la precedente build storica 0.2 e funzionano come percorso alternativo esplicito tramite `SYMBIAN_TOOLCHAINS`.

## Riprodurre da sorgenti sul proprio Linux

```bash
cd DalvikE63
sudo apt-get update
sudo apt-get install libc6-i386 lib32z1 lib32stdc++6 bison flex unshield \
  gcc g++ perl make patch zlib1g-dev libssl-dev curl unzip python3 \
  python3-pil fonts-dejavu-core openssl
# Isolare l'SDK >1 GiB nella cartella build/ esclusa dallo snapshot:
export SYMBIAN_TOOLCHAINS="$HOME/build/e63-local"
mkdir -p "$SYMBIAN_TOOLCHAINS/s60-fp1"
# Riutilizzare i due archivi GnuPoc/GCCE conservati senza duplicarne i byte:
ln -s "$HOME/toolchains/gnupoc-downloads" "$SYMBIAN_TOOLCHAINS/gnupoc-downloads"
# Scaricare solo lo ZIP SDK per LEGGERE la licenza, senza installarlo:
curl -fL --retry 4 -o "$SYMBIAN_TOOLCHAINS/s60-fp1/S60-SDK-200634-3.1-Cpp-f.1090b.zip" \
  'https://archive.org/download/nokia_sdks_n_dev_tools/S60-SDK-200634-3.1-Cpp-f.1090b.zip'
echo 'f445cf1f7ddaa5ec5d5a8a806271db8880c9a430150b1cfcdc7de9d9bd758858  '"$SYMBIAN_TOOLCHAINS/s60-fp1/S60-SDK-200634-3.1-Cpp-f.1090b.zip" | sha256sum -c -
unzip -p "$SYMBIAN_TOOLCHAINS/s60-fp1/S60-SDK-200634-3.1-Cpp-f.1090b.zip" Nokia_EULA.txt | less
# Solo se hai letto e deciso di accettare la licenza/patch locali:
NOKIA_SDK_LICENSE_ACCEPTED=1 bash tools/bootstrap_symbian_fp1.sh
bash tools/build_symbian_fp1.sh
python3 -m unittest discover -s tests -q
# Controllo indipendente dei dati effettivamente inseriti nel SISX:
export EPOCROOT="$SYMBIAN_TOOLCHAINS/s60-fp1/sdk/"
python3 tools/verify_symbian_sis.py e63os build/symbian/e63os.sisx
python3 tools/verify_symbian_sis.py e63bridge build/symbian/e63bridge.sisx
# Dopo aver copiato il SISX verificato in release/, rimuovere solo la toolchain temporanea.
# Non cancellare $HOME/toolchains/gnupoc-downloads/.
```

`SYMBIAN_TOOLCHAINS=/percorso` cambia la cartella della toolchain. **Non usare `/tmp` se è un tmpfs da ~1 GiB**: il CAB estratto e l’archivio SDK superano quello spazio e `unshield` può fallire per disco pieno; questa nuova build ha usato una directory temporanea su disco poi rimossa. Il bootstrap **non copia** l’SDK nel progetto. Il suo installatore GnuPoc riorganizza l’SDK e applica patch a una copia locale: non è l’installer Windows originale. È stato superato anche il build di `HelloWorldBasic` `GCCE/UREL`. Verificare il risultato con `elftran -dump s "$EPOCROOT/epoc32/release/gcce/urel/e63os.exe"` (SID `e0b63e02`, nessuna capability) e con l’analogo bridge (SID `e0b63e01`, `NetworkServices`). **Attenzione:** `abld` può restituire exit status 0 *anche dopo errori C/C++*: lo script cancella gli EXE precedenti e controlla il log e la loro rigenerazione.

Gli output firmati e la **chiave privata di test** finiscono solo in `build/symbian/` (escluso dal pacchetto sorgenti). `openssl req -x509 -newkey rsa:2048 -sha1` è usato per la compatibilità con la firma SIS Symbian 9.2, non come sicurezza moderna; SHA-1 non è raccomandato per nuovi sistemi. Firma/autocertificazione non garantiscono che il telefono accetti o avvii il programma. Certificato della **prima release 0.2.1/bridge (conservata)**: impronta SHA-256 `75:18:01:0E:9B:54:35:7A:27:5A:FD:AD:03:8C:AB:7B:C6:F6:66:76:7F:43:CA:AC:8A:F5:C4:D1:3B:6B:0A:27`, valido **2026-09-26 23:24 UTC → 2028-09-25 23:24 UTC**. È stato rigenerato perché la chiave vecchia (nel precedente `build/` escluso dagli snapshot) non era disponibile; su un’installazione precedente il cambio di firmatario potrebbe impedire l’aggiornamento diretto. L’orologio E63 deve essere nel periodo di validità per una prova. Per la nuova prova **solo UI 0.2.2**: certificato di test SHA-256 `12:8A:BE:1B:28:7B:5E:8B:32:05:5B:9D:06:5C:2C:BA:6F:B3:61:0A:C5:BE:A0:3D:BF:EF:D0:12:00:4A:54:0F`, valido 2026-09-27 00:38:03 UTC → 2028-09-26 00:38:03 UTC. Il bridge consegnato resta quello precedente. La chiave locale non va inviata né usata come identità di produzione; una nuova build/chiave produrrà hash SISX diversi.

La toolchain estratta occupa **~1,4–1,5 GiB** (`SDK` ~1 GiB + archivio ~355 MiB, GCC/GnuPoc). Per la build 0.2.2 è stata installata temporaneamente sotto `~/build/e63-local/`, **rimossa dopo aver verificato e copiato il SISX** per non superare i ~128 MiB dello snapshot. Solo i due piccoli archivi GnuPoc/GCCE sotto `~/toolchains/gnupoc-downloads/` sono conservati; **lo ZIP SDK deve essere riscaricato** se servirà un’altra build, usando URL/hash qui riportati. Anche i pacchetti `apt` possono non sopravvivere a un nuovo ambiente. L’archivio sorgenti contiene **solo codice nostro, asset originali del progetto e pack font/immagini derivato**: niente SDK Nokia o chiavi private.

## Che cosa c’è davvero nei SISX

- `e63os.sisx`: AppArc/UI S60 `symbian/e63os_app.cpp`, VM `dex_preflight.c` + `ui_event_vm.c`, renderer `rgb565_painter.c`, risorsa/registrazione menu, **il `classes.dex` originale del Launcher.apk** (40.276 B, confronto byte-per-byte all’atto del build) e `e63assets.bin` (11 PNG originali del JAR/APK resi RGBA e 6.264 maschere/metriche DejaVu). I dati vanno a `C:\private\E0B63E02\...`; l’EXE mostra tramite `CFbsBitmap` il **vero paint guest DEX** a 320×240 per sette schermate, con clock Symbian locale, batteria sconosciuta `?` e Wi‑Fi non dichiarato attivo. Gli oggetti LCDUI sono *seminati dall’host* perché `startApp` non è supportato. Il font pack è generato offline con Pillow 12.3.0 e DejaVuSans.ttf SHA-256 `57f73e11f51999432bf7ab22ce55b6f945d5eca1bf824404cfa9ec2e3718c84e`; un testo fuori cache fallisce chiuso, non viene rimpiazzato da un layout host. Non è il runtime Android 4.2 completo.
- `e63bridge.sisx`: server console `symbian/e63bridge.cpp` legato al **127.0.0.1:27463**, `NetworkServices`, frame autenticato solo per **PING**, più `e63bridge_launch.exe` registrato nel menu AppArc come “E63 Bridge”. **Verificato sul telefono dell’utente:** il launcher apre la console, mostra PIN e il JAR MIDP riceve `SIS bridge: PONG`. Nessuna API file è esposta.
- Non inclusi: Android completo in RAM sul Nokia, import da C:, FileManager Nokia reale, runtime `E63Midlet.startApp`, schermate Settings/Login/Store/Files native C99, Forms/Unicode, bridge per file/privilegi. L’INSTALL → OPEN verificato resta nel **prototipo PC**, non nel SISX parziale.

## Gate sul dispositivo ancora aperto

1. Prima del test eseguire backup E63 e leggere l’avviso di firma/autocertificazione; verificare ora/data del telefono. Non installare i pacchetti se non si accettano il rischio dei prototipi e l’eventuale EULA dell’SDK. `e63os` non usa `AllFiles` né capability extra; `e63bridge` chiede `NetworkServices`.
2. Per il nuovo input installare `release/e63os-0.2.2-back-dpad.sisx` dopo backup: la 0.2.1 mostrava già Home e tasti Fn. Verificare **Fn+7 → Quick Settings → softkey sinistro (non freccia sinistra) → Home**, poi pad destra/sinistra per muovere la selezione. Certificato nuovo: se l’aggiornamento è rifiutato, backup e disinstallare solo la UI 0.2.1, non bridge/JAR. **Un errore o un frame nero è un fallimento da riportare, non un successo inferito dal build.** La schermata Settings non è nel subset C99 e può non dipingersi; tornare a Home col softkey sinistro o Fn+0 nella 0.2.2, se confermato dal telefono. Il telefono E63 non è touchscreen.
3. **Già provato sull’E63 dell’utente:** aprendo il bridge compare una console con PIN; dal **JAR/JAD MIDP 2.0** `Settings → SIS Bridge → Connect` ha prodotto `SIS bridge: PONG`. Non aprire una seconda istanza del server; la dicitura «3 failed attempts stop server» è un avviso, non significa che i tre tentativi siano già falliti. Tre tentativi effettivamente respinti lo arrestano. Il server è **solo PING**, senza API file; il PIN non è adatto a proteggere operazioni su file.
4. Portare font/Forms/native file import e tutte le schermate, validare la firma/trust dei pacchetti e la persistenza/limiti sotto `C:`; riprovare con foto/log hardware. In alternativa EKA2L1 richiede ROM/firmware S60v3 ottenuto lecitamente; il test SIS dell’emulatore non prova la MIDlet JAR su E63.
